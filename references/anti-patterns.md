# 反模式与禁忌用法

> 这些做法会让你"攒了一堆用不上的条目"或"把退化写进库"。每条都给改进对照，照做能直接避坑。

## 反模式 1：把库当垃圾桶——只 add 不复用

**现象**：任务一跑通就 `add`，之后再也没 `find` 过，条目永远停在 `captured`，`guard` 永远 OPEN。
**后果**：库膨胀、闭环率为 0，`guard` 在收尾自检时直接失败，任务无法宣布完成。
**改进**：
- `add` 之后，下一个同类任务先 `find --query <关键词>` 复用；
- 复用完 `record --score <验证分>`；
- 发现更优解才 `optimize`。**存了就要用**，库不是垃圾桶。

## 反模式 2：为通过 optimize 硬凑更高分

**现象**：`optimize` 被 REJECTED，就反复换个稍高分往上提，直到通过。
**后果**：把"并不更优"的改动写进库，棘轮失效，库质量被稀释。
**改进**：REJECTED 是对的——新分必须**严格高于** `baseline_score`。只有你真实验证过更好才提；否则接受 REJECTED，库保持不变。

## 反模式 3：把真实业务数据 / 密钥塞进条目

**现象**：`--approach` 里写"对接客户 X 的 API，key 是 xxx"，`--description` 写含个人信息的原文。
**后果**：库变成敏感信息泄露面，提交到仓库即外泄。
**改进**：条目只存「拆解方式 + 关键维度」这类经验；密钥 / 个人信息脱敏或外置；误存了用 `optimize` 改掉或删条目，彻底重置直接删库文件（见 faq-deep D5）。

## 反模式 4：拿 find 当语义检索用

**现象**：搜「竞争分析」找不到「竞品报告」，就认为技能坏了。
**后果**：同义词 / 近义词漏召回，复用率上不去。
**改进**：`find` 是字符重叠匹配，不是语义检索。用 `--tags` 给同义任务打同一组标签（都打 `competitor`）；或先 `list` 看全量；要真语义检索请外接向量库（见 faq-deep D3）。

## 反模式 5：撞步数上限后疯狂 retry

**现象**：`optimize` 反复 REJECTED，步数见底，又疯狂重试想绕过。
**后果**：步数快速耗尽，正常自优化也被卡死。
**改进**：STOP 是硬代码防死循环。先 `audit` 看清必要性 → `reset-steps` 清零 → 或 `--max-steps` 提高上限。注意 **REJECTED 也计步**，反复凑分会快速耗尽。

## 禁忌用法清单（绝对不要）

- ❌ `--approach` 写空或占位（"研究一下"）→ 硬拒，库不接受垃圾条目
- ❌ `optimize` 的 patch 改 `id` / `baseline_score` 等结构字段 → REJECTED
- ❌ 多 Agent 并发写同一个 `--store` → 读到过期数据、丢条目
- ❌ 把本库当通用向量 / 语义检索引擎 → 它只做字符 + 标签匹配
- ❌ 把库内容当确定事实对外宣称 → 库是你的经验草稿，需你验证后再用
